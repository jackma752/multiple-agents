# 会话页面 `/chat`：前端演示闭环（2026-10-22）

**2026-10-26 复制修复**：阶段轮询不再无条件重建消息 DOM；文字选中时保留选区，清除选区后
应用积累的消息变更。回复及调用卡增加复制按钮。真实浏览器离线验证见
[模型与协作集成](model-collaboration-integration.md)，其中包含当前8080启动入口。

分支 `feat/chat-frontend`，基于 `feat/async-tool-approval`。和 `/ui` 一样是零构建单页（`apps/api/agenthub_rt/static/chat.html`），旧控制台 `/ui` 没有改动。全程离线，没有真实模型调用。

## 启动

```powershell
cd E:\plug\agent-hub\.worktrees\chat-frontend
& 'E:\plug\agent-hub\.venv\Scripts\python.exe' tools\demo\serve.py --port 8170 --appserver-stub demo --data-dir var\demo-chat
```

然后打开 `http://127.0.0.1:8170/chat`。

- `--appserver-stub demo`：走 app-server 传输，但对接的是内置的离线 stdio 桩，不启动 Codex，也没有模型。
- `--data-dir`：数据库和运行目录与默认的 `var/` 分开，也不会碰 8080 上的服务。
- token 与 `/ui` 一样在页面里输入，留空时使用开发默认值。token 只保存在本标签页的 sessionStorage 中，不进 URL，也不进 localStorage。

`demo` 桩的脚本是固定的，不读用户输入：

1. 分几段流式输出一句话（每段间隔 0.25 秒）；
2. 请求执行 `dir C:\stub`；
3. 收到回答后，按回答的内容说一句结束语（批准 / 拒绝 / 未批准各不相同），然后结束本轮。

## 页面做了什么

| 环节 | 实现 |
|---|---|
| 发消息 | `POST /api/conversations/{id}/invocations`，只生成**待审批调用**，不会直接调用 Agent。没有会话时先自动建一个 |
| 批准 | 调用卡片上显示将调用哪个 Agent、发送什么内容、是否续接 thread；用户点击“同意并调用”后，页面先批准，再 `POST /run`（202，后台执行） |
| 逐步输出 | 用 `fetch` 流式读取 `/events/stream`（`EventSource` 无法带 Authorization 头）。`stream.delta` 的文本由服务端组装后推送，页面放进“生成中（临时）”气泡 |
| 工具卡 | 收到 `tool_approval.requested` 后，到鉴权接口读取卡片详情，显示命令、目录、理由和倒计时。“批准这一次”会带上 `card_hash`，“拒绝”直接发送；卡片最终显示 已批准 / 已拒绝 / 已过期（按拒绝处理）/ 已作废，以及实际发出的决定 |
| 终态 | 收到助手 `message.created` 后重新读取消息，用最终回复替换临时气泡；`unknown` 显示为“状态未知：名额保留，需人工裁决” |
| 停止 | 执行中显示“停止本地进程”，结果提示“远端停止未确认，名额保留” |
| 刷新恢复 | 会话 ID 放在 `#hash` 中。重新加载时先读消息，再从 seq 0 重放事件，按 seq 去重、每条只处理一次；断线后带 `Last-Event-ID` 续读；游标超前（409）时整页重新同步 |
| 新一轮 | 只有该 Agent 最近一条回复带有 `native_session`、并且没有执行中或未知状态的调用时，“续接上一轮”才可勾选 |

安全约束：
- 所有文本（消息、命令、模型输出）一律用 `textContent` 插入，页面中没有 `innerHTML`、`eval` 或 `new Function`。
- 页面不会自动批准任何东西，每次批准都是用户对某一张具体卡片的点击。

实测方式说明：第 1 轮的“发送”和“同意并调用”是真实的鼠标点击。之后浏览器面板被隐藏、不再绘制，坐标点击无法执行，所以后续操作改为用 `form_input` 填表，并用脚本调用按钮自己的 click 处理函数——走的是同一条代码路径，但不是物理指针事件。

## 实测中发现并修复的问题

1. **页面冻结**：渲染原先用 `requestAnimationFrame` 合批，而窗口没有绘制时（后台标签页、被遮挡）它会暂停，导致事件已经到达、界面却不刷新。现改为 16 毫秒的定时器。
2. **点击丢失**：待决卡片的倒计时原先每秒整页重绘，按钮在鼠标按下和抬起之间被替换，点击就会丢失。现在倒计时只更新自己的文字；按住鼠标期间推迟重绘。
3. **卡片排在输出前面（后端）**：卡片可能比它之前的增量文本更早进入事件流，原因有两个：
   - StreamSink 会把增量缓冲约 0.2 秒；
   - 客户端把请求和通知放在两个队列里，pump 可能先处理到请求。

   现在建卡前先处理已排队的通知，再 flush StreamSink，所以前面的输出一定排在卡片之前。`tests/http/test_chat_page.py` 检查了这一点：卡片前的增量正好是开场白，卡片后的增量正好是结束语。
4. **无障碍**：“续接上一轮”复选框补上了 `aria-label`。

## 中断、原生子 Agent 与用量（2026-10-22 续，分支 `feat/interrupt-stop`）

- **中断本轮**：只有调用在执行、并且模型回合已经开始时才能点击。页面分三种情况如实显示：
  - “已请求中断 → 已收到终态：已取消（provider 确认已中断）”；
  - “已请求中断，服务端已接受；尚未收到终态，远端停止未确认，名额保留”；
  - “服务端未接受（原因）；名额保留”。

  刷新后，中断记录会从 `task.interrupt_requested` 事件恢复。“停止本地进程”仍然保留，它的含义不同：只结束本地进程，远端是否停止不作确认。
- **原生子 Agent**：收到 `stream.native_agent_observed` 时，在调用卡片上提示“检测到原生子 Agent：spawnAgent → thread …。它不在 Hub 的审批与配额内，Hub 只能观测、不能控制。”回合结束时如果还有子 Agent 没有结束证据，提示“父回合实际终态：completed；原生子 Agent（thread …）没有可信的结束证据：调用保持未知，名额保留……”。
- **中断生效点**：中断记录中会写明“中断生效：本调用的工具审批已关闭，不再认领新的决定（作废 N 张待决卡，拦截 M 个未发送的决定）”。如果关闭前已有决定被认领，会另外说明“可能仍会发出、无法撤回，是否发出以卡片送达状态为准”。卡片的送达状态包括：“已认领，可能正在发出（无法撤回）”“已发出：…”（只表示写操作已经返回）和“未发送（中断或停止后被拦截）”。
- **用量**：回复上显示 provider 报告的 token 用量，例如“用量 输入 11 / 输出 2”。

浏览器实测（端口 8170，demo 桩，新的数据目录）：
- 批准之后，工具卡在等待决定时点击“中断本轮”。页面显示“已请求中断 → 已收到终态：已取消（provider 确认已中断）”，回合结束状态为 `interrupted`，工具卡变为“已作废 / 未发送”，部分输出作为回复保存并带有用量。
- 刷新后以上内容完全恢复（`last_seq` 16），控制台没有错误。
- “服务端已接受但没有终态”和原生子 Agent 这两种情况，demo 桩无法演示，由自动测试覆盖。

## 会话切换、重连、命令展示与监督模式（2026-10-23，S6-4 前置）

演示时发现两个缺陷，按用户要求离线修复，并补齐了网页上的监督模式入口。

**1. 会话切换与事件流竞态**
- **根源**：`select()` 在 `await loadMessages()` 之后才读取共享的 `streamGen`，两次交错的 `select()` 会让旧会话也拿到一个仍有效的编号。结果是两条事件流同时写入当前会话的状态，并共用同一个 `lastSeq`。旧会话的流用当前会话的游标重连时得到 409，它触发的重同步再把当前会话清空。表现为：每次重连（约 25 秒）后，流式文字、回合状态和工具卡都消失。
- **修复**：
  - 每次 `select()` 先开启新的视图代际 `S.viewGen`。消息、卡片、流帧、重同步等每个异步结果都带着发起时的代际，代际过期就丢弃。旧会话的流在下一帧就自行退出。
  - 普通重连（服务端超时后正常结束）从 `lastSeq` 继续，已显示的内容全部保留。
  - 409 才完整重建：清空状态、重读消息、从 seq 0 重放事件流，恢复流式文字、回合状态和工具卡。
- **多建空会话的根源**：新建的会话还没选中时就可以提交消息，`send()` 看到 `S.cid` 为空，会再建一个。现在 `createConversation()` 是唯一的创建入口：“+ 新会话”和 `send()` 共用正在进行的那一次创建，创建期间“+ 新会话”按钮禁用。
- 页面的 `<main>` 上新增诊断属性 `data-reconnects`、`data-resyncs`、`data-created`。

**2. 命令展示**（后端 `command_view`，只用于展示）
- 改为严格的 POSIX 拆分，只接受 `shlex_join` 会产生的形式：安全字符组成的裸词、`'...'`，以及 `"..."`（其中只有 `\\`、`\"`、`\$`、`` \` `` 是转义）。
- 未加引号的反斜杠（POSIX 下是转义，Windows 下是路径分隔符）、未加引号的 shell 语法或非 ASCII 字符、引号不配对、换行，都判为“无法可靠拆分”。这时页面只显示原文，不显示任何改写后的命令。
- Windows 路径、空格和嵌套引号都有测试覆盖。S3 的严格命令范围判断（`classify_command`）在另一个模块里，没有改动。

**3. 监督模式入口**
- 创建调用时，“执行模式”必须在“严格模式 / 用户监督模式”中明确选择，默认是“请选择”。选项上标出当前适配器的准入状态。每次发送之后，模式复位为“请选择”。
- 用户监督模式的调用卡上有一个“本次调用”的边界同意框，默认不勾选；不勾选就不能点“同意并调用”。批准请求只在这次勾选时才带上 `accept_unmanaged_native_agents: true`。无论成功与否，同意状态都会清除，不会沿用到下一次调用，也不会跨会话保留。
- 后端检查保持不变：缺少同意时，服务端返回 409 `boundary_consent_required`。

### 浏览器验收（内置浏览器，端口 8171，demo 离线桩）

| 验收项 | 结果 |
|---|---|
| 页面刚加载时点“+ 新会话”，紧接着选模式、输入并发送 | 只发出一次 `POST /api/conversations`，消息进入同一个会话，`data-created=1` |
| 严格模式调用批准后，工具卡待决期间跨过重连 | 本会话共 4 次事件流请求，即重连 3 次。流式文字 1 段、工具卡 1 张、“模型回合已开始”都保留；倒计时从 119 秒正常递减到 53 秒；重同步 0 次 |
| 切换到另一个会话再切回 | 旧会话的流被中止（`ERR_ABORTED`），任何时刻只有一条流。切回后文字、卡片、回合状态都恢复，没有重复，倒计时剩 12 秒 |
| 跨过重连和切换之后点“拒绝” | 卡片显示“已拒绝 · 已发出：decline”，调用“已完成 · 严格模式”，最终回复 1 份 |
| 用户监督模式的调用 | 带“用户监督模式”标签；同意框未勾选，“同意并调用”禁用；勾选后才可用。批准返回 200，工具卡拒绝正常 |
| 下一个监督模式调用 | 同意框仍未勾选，批准按钮禁用（没有沿用）。点“拒绝”后，调用为 rejected |
| 发送后的模式选择 | 复位为“请选择”，发送按钮禁用，提示“请先选择执行模式” |

本轮浏览器会话中没有出现 409。控制台里的 `ERR_CONNECTION_REFUSED` 来自服务重启前的旧页面，404 来自预览打开时请求的根路径 `/`。
