# P6 全文缺失与用户补充流程

日期：2026-10-29。来源：用户在当前对话给出的两种方案及补充不完整时的继续规则。

状态：P6.0 功能规划与验收设计，尚未实现、尚未运行验证。本轮不修改运行代码、公共类型或数据库；后续开发仍需用户另行决定。

关联：[P6 总方案](p6-paper-pipeline.md)、[上游调研](p6-upstream-research.md)、[阶段模板设计](p6-academic-prompts.md)。本需求将论文补充入口纳入首版必需能力，替代此前“是否提供首版 PDF 导入待定”的安排。

## 1. 创建任务时选择策略

请求表单增加「无法读取全文时怎么办」，选择随任务和阶段授权一起保存，不由模型替用户选择。

| 策略 | 首次发现缺失全文 | 首次未作选择 | 选择补充后 |
| --- | --- | --- | --- |
| 方案一：可按现有资料继续 | 汇总缺失清单，询问「补充全文」或「不补充，按现有资料继续」 | 请求发出后 30 分钟未作选择，默认不补充并按现有资料继续 | 取消本次 30 分钟倒计时，等待补充，不再自动跳过 |
| 方案二：先等待补全文 | 汇总缺失清单，停在补充资料请求处 | 不设自动继续时限，持续等待 | 补齐并完成阅读后继续；部分补充按第 4 节再次询问 |

这里的「停在请求位置」指：已完成检索和全文可用性检查，在阅读阶段的补充资料请求处等待，不进入综合分析或写作；不是创建研究请求后就停止检索，否则无法知道哪些论文缺失全文。

方案二也允许用户在本轮补充不完整后的询问中明确选择不再补充，转为按现有资料继续。它没有超时默认继续，不把用户沉默当作放弃补充。

## 2. 一次性返回完整清单

对当前任务纳入阅读的全部论文完成摘要读取和有界的全文获取/解析检查，再统一发出一份缺失清单。不按每篇下载失败逐条打断用户；与主题无关且已排除的候选论文不混入补充请求。

清单覆盖无全文入口、下载失败、文件损坏/加密、解析为空或首版无法处理的扫描件等情况。系统记录具体原因及已有摘要状态；模型额度不足等全局运行故障另走现有等待/错误流程，不误报为论文全文缺失。

每条以参考文献形式显示，至少包含已知作者和论文题名，年份、期刊/会议、DOI、原始链接有则附带；缺失元数据明确标记，不能编造作者、页码或 DOI。提供整份复制/下载和逐条补充入口，编号与稳定 paper_id 关联。

展示结构示意（不是真实文献）：`[编号] 作者. 论文题名. 年份. DOI 或来源链接`，旁边单独显示缺失原因、摘要是否可读、补充状态。格式化由真实元数据完成，不额外调用模型编造引用。

只有全部检查完成、当前缺失集合可确定时才发出本轮请求；未知/仍在途的获取任务不能被当成已确认缺失。补充后的后续清单一次性列出所有仍未解决项，已解决项折叠保留，避免重复要求同一论文。

## 3. 方案一的 30 分钟规则

首次缺失请求进入 `awaiting_choice` 时记录请求时间和截止时间，截止为 30 分钟后；UI 展示剩余时间与超时默认行为。关闭页面、刷新或重新连接不会重新开始计时，也不生成另一份请求。

- 选择不补充：关闭补充请求，保存用户决定，阅读阶段按现有全文和摘要继续。
- 选择补充：进入 `awaiting_files`，清除本次选择截止时间，等待上传、引用文件或文件地址；不能再在原截止时刻自动继续。
- 未作选择到期：保存 `timeout_continue` 原因，按请求阶段已确认的方案一规则继续。该授权仅覆盖跳过补充，不扩大模型、文件或网络权限。
- 开始上传/提交文件引用的服务端入口必须先原子记录“选择补充”，不能让文件正在传输却被倒计时跳过。客户端尚未送达服务器的点击不能伪装成已受理。

超时与用户选择并发时，以后端一次性状态转换为准：一旦补充选择被受理，超时不能再生效；一旦超时继续已提交，晚到补充不能悄悄插入正在分析的资料版本，应告知用户并走显式重新纳入/重算流程。

## 4. 补充完整与不完整时的交互

允许多文件上传、选择/引用已授权本地文件、提供文件路径或 HTTP(S) 文件地址。每份资料可以关联一个缺失论文条目，也可以批量提交后辅助匹配；匹配不明确需用户确认，不按文件名相似度静默认定为原论文。

用户以「提交本次补充」结束一个批次。上传过程中不逐文件追问“是否继续补充”；批次提交后统一获取/解析、核对论文身份与全文可读性，再一次性计算剩余缺失列表。仅收到路径或一个 URL、文件已上传但无法解析、补成另一篇文章，都不算补齐全文。

| 本批结果 | 下一步 |
| --- | --- |
| 全部缺失论文已补成可读全文 | 阅读新增全文，保存证据与阅读深度，再进入下游阶段 |
| 只补充了一部分，或仍有文件不可读 | 一次性返回全部剩余清单，只询问一次「是否继续补充？」 |
| 用户回答继续补充 | 再开放上传、引用或文件地址入口，等待下一批次；不设置 30 分钟自动跳过 |
| 用户回答不再补充 | 保留本轮已有效补充的全文，先完成这些论文的阅读；其余按已有摘要/资料继续，并记录未读全文项 |
| 用户尚未回答是否继续补充 | 保持等待，不把沉默视为拒绝；已经选择补充的用户不套用首次 30 分钟默认继续规则 |

上述不完整处理同时适用于两种方案。每个已提交批次只产生一次后续询问；用户选择继续并提交新批次后，如果仍未补齐，再按同样规则询问，不能限制成“整个任务只能补一次”。有效补充不重复上传、不重复阅读。

收到全部必要资料或用户明确不再补充后，才释放本次阅读关口。之后产生的新缺失资料集合（如用户批准追加检索）使用新的请求版本，不反复重发已关闭的请求。

## 5. 等待、恢复与资料版本

建议新增的领域状态如下，不在本轮把这些状态写入已有 StageRules 或运行枚举：

| 状态 | 含义 | 自动继续条件 |
| --- | --- | --- |
| `checking_fulltext` | 全部目标论文的获取/解析检查中 | 没有缺失时进入待阅读结果；否则汇总 |
| `awaiting_choice` | 仅方案一的首次补充选择 | 只有未选择且达到已保存截止时间才可超时继续 |
| `awaiting_files` | 方案二初始等待，或用户已选择补充 | 无超时自动继续 |
| `validating_batch` | 接收并校验已提交资料 | 只转为补齐，或进入再次选择 |
| `awaiting_more_choice` | 本批不完整，等待继续补充/不再补充 | 无超时自动继续 |
| `resolved` | 全部补齐，或按明确决定/方案一超时关闭请求 | 完成有效补充的阅读后可进入下游，仍须通过原授权与预算门禁 |

研究任务可显示 `waiting_input`，与用户手动暂停、额度等待和执行未知分开。等待不占用运行中的 Agent 并发槽，不周期调用模型询问用户；HTTP 下载/解析等工作仍受原资源规则约束。

补充请求、目标论文集合、方案、选择和时间、剩余项、各批次及接收哈希、匹配和解析结果、阅读结果、资料版本与下游幂等键均需持久化。去重键包含 task/input_version/request_id/round；消息重复发送、刷新、重复点击和重启不得重复创建请求或触发下游。

后台退出期间不会凭空执行任务。重新运行后按已保存的选择/截止时间核对：方案一确实未选择且已过期才可默认继续；方案二和已经选择补充的情况继续等待。人工暂停、已停止、阶段失效或执行状态未知时不得因计时到期启动新调用，恢复后先核对状态和现有授权。

补充行为不隐式重开原生 Agent 线程或更改已消费调用快照；后续阅读使用新的资料快照，沿用同一根任务计量。已阅读全文按内容哈希与任务版本复用，不重跑原有检索和已完成阅读。迟到或主动追加资料如影响已完成综合/写作，需要明确新版本及受影响下游重算，不静默替换旧证据。

## 6. 数据与输入契约待补项

| 对象 | 需补信息 |
| --- | --- |
| ResearchTask | `fulltext_policy`（两种明确方案）、当前阅读关口、已确认策略版本 |
| FulltextSupplementRequest | request/task/input_version、当前缺失集合、首次请求/当前轮次、状态、创建/截止/决定时间、决定来源、继续原因 |
| MissingFulltextItem | paper_id、参考文献元数据快照、原链接、摘要状态、缺失原因、已补文件/剩余状态 |
| SupplementBatch | batch/request/round、用户提交时间、上传/引用/地址、受控文件位置与内容哈希、匹配/解析/阅读状态及逐项错误 |
| PipelineCheckpoint | 当前请求和批次、等待状态、截止时间、剩余项、已读取资料版本及继续是否已经提交 |

现有文本文件引用只接受 UTF-8 文本，不会自动获得 PDF 上传/解析能力；P6 要提供自己的受控论文导入与解析路径。用户提供的本地路径仍按宿主文件授权读取；网络地址须经现有拟补资源规则核对，不能因为是补充入口就接受任意网络/路径访问。

方案与缺失清单由结构化数据决定；模型可以解释资料，不能修改计时、假称用户已经拒绝或把未读全文标成已读。补充正文、匹配后的片段和用量按原研究数据规则存储，不进入 Git、安装包或普通日志。

## 7. 继续后的结果约束

「按现有资料继续」指使用已获得的全文、用户有效补充和可读摘要。没有全文就保留摘要级证据标记；连摘要也没有的只保留题录/缺失信息，不能从题名补造结论。

成品必须列出全文读取数量、摘要级数量、缺失清单、用户跳过/超时继续的原因与影响。用户允许继续不等于论文变成全文已读或质量检查自动通过；全文范围受限与其他关键质量问题仍独立展示。资料完全不足以支撑正文时返回资料不足说明和已得资料，不编造综述结论。

## 8. 必须覆盖的验收场景（待开发后执行）

1. 请求阶段两种策略可选择并绑定任务；模型无法自行切换。
2. 多篇论文同时无法读取，首次只返回一份完整、可复制的参考文献清单，包含作者、题名和真实可得元数据；不存在逐篇重复弹窗。
3. 方案一明确不补充立即释放关口；明确补充后原倒计时失效；30 分钟未选择只触发一次默认继续。
4. 方案二超过 30 分钟仍等待；阅读阶段之前的检索/可用性检查已完成，下游未启动。
5. 批次只补部分时统一展示全部剩余项，每批只询问一次；选择是再等待下一批，选择否保留已补资料并继续；两方案行为一致。
6. 用户已选择补充或尚未回答再次补充询问，等待超过 30 分钟不会跳过；上传期间不误触发超时。
7. 重复提交、计时与用户选择竞争、刷新、关闭浏览器、重启、人工暂停及阶段停止均不会重复或越权启动下游；过期核对不重置截止时间。
8. 错论文、同名文件、重复内容、坏 PDF、扫描件、不可达地址、路径读取失败和模糊匹配都有逐项状态，不误报补齐。
9. 阅读有效补充后才进入分析，已完成论文不重读；未补条目始终保持摘要/题录级标记，引用和最终覆盖说明一致。
10. 所有补充读取、模型调用与后续继续仍受相同根任务的资源授权和预算约束；没有材料时不生成无依据正文。

文档可以检查流程和交叉引用，但不能以文档检查通过宣称上述交互或计时已实现。
