# P4.6 自动执行：实现设计（分支 `feat/p46-autopilot`）

需求见 `E:\plug\AGENT_HUB_AUTOMATION_REQUIREMENTS.md`。本文写实现方案和各步范围，P4.6a 先做，b、c、d 依次跟进。本文不授权任何真实运行。

## 1. 授权模型

- 授权仍只有一个执行入口：`PolicyService.consume`。它在事务里核对快照、策略版本、审批、停止和暂停状态以及名额，通过后才启动适配器。P4.6 不新增绕过它的路径。
- 授权有两种来源：
  - **逐次同意**（手动模式）：沿用现有审批卡。
  - **阶段授权**（自动模式）：登录用户在页面上启动一个阶段时，后端写一条阶段记录（`stage_runs`），内容包括目标、完成标准、规则、执行边界和规则哈希；用户监督模式的边界同意也在这里勾一次。
- 调度器为阶段内的每一步生成普通调用和审批，然后按规则代为批准，并写一条授权来源记录（`stage_grants`：审批 → 阶段、步骤、规则）。
- 执行入口新增一项检查：凡是由阶段批准的调用，阶段必须仍在进行中，且没有过期；否则拒绝（`stage_not_active`），适配器不启动。所以阶段暂停、停止或过期后，已批准但还没执行的调用也启动不了。
- 规则只能由登录用户通过接口设置。Agent 的回复只能提出计划内容和工具请求，不能修改规则，也不能给自己授权。
- **前置条件“先跑通一次”**：
  - 启动阶段时，对规则里的每个 Agent 检查是否已有一次满足以下条件的成功调用：同一 Agent、同一适配器身份（binding）、同一执行边界，由用户逐次批准（不是阶段批准）。没有就拒绝（`stage_not_proven`）。
  - 身份必须相同，所以用桩跑通的只能开启模拟的自动执行。
- 计划需要子任务时，启动阶段会顺带开启协作扩展。开启协作会生成新的策略版本，按现有规则作废未消费的手动审批，页面在确认框里提前说明。

## 2. 阶段规则（契约 `agenthub.stage`）

| 字段 | 含义 |
|---|---|
| `agents` | 允许使用的 Agent |
| `plan` | `none`：不拆分，由主 Agent 单次完成；`current`：沿用会话里最新的手写计划；`agent`：先请主 Agent 拆分，读回后执行 |
| `main_agent` / `review_agent` / `collect_agent` | 主调用、审阅（可不设）、汇总使用的 Agent，都必须在 `agents` 里 |
| `max_calls` | 本阶段最多由规则批准的调用数（1–50），同时仍受树策略的调用上限和预算约束 |
| `tool.command_prefixes` | 允许自动放行的命令前缀，每行一条 |
| `tool.allow_file_changes` | 是否自动放行文件修改请求 |
| `retry_limit` | 普通错误首次失败后的重试次数，默认 3（P4.6b 使用） |
| `auto_resume` | 额度恢复后是否自动续跑，默认开（P4.6c 使用） |

**工具规则**（`agenthub.stage.tool_decision`，纯函数）：
- 只对 Codex app-server 有意义。Claude Code CLI 本来就关了工具。
- 命令请求自动放行，需同时满足：
  - 命令能被拆成参数；
  - 有效命令（去掉 PowerShell 或 cmd 外壳后）以某条前缀开头，且在单词边界处结束；
  - 不含 `;`、`&&`、`||`、`|`、`>`、`<`、反引号、`$(` 等串接或重定向符号；
  - 如果命令里出现敏感词（删除、推送、合并、部署、联网下载等），匹配的那条前缀本身必须写出这个词。例如前缀 `git` 不能放行 `git push`，必须单独写 `git push`。
- 文件修改请求只在 `allow_file_changes` 为真时放行。扩大可写根目录（`grantRoot`）的请求一律拒绝。
- 其余请求自动拒绝，不等人点。拒绝原因写进卡片和阶段事件，Agent 收到拒绝后可以换办法。
- 适配器本身是“只能拒绝”模式时，放行也会被改写成拒绝。这条原有规则不变。
- 阶段暂停后，进行中调用新开的工具卡交回用户手动决定。

## 3. 调度（P4.6a）

`agenthub_kernel.autopilot.Autopilot.tick()` 每次推进所有进行中的阶段。每一步都在 `BEGIN IMMEDIATE` 里创建调用，`client_request_id` 由阶段和步骤固定生成，重复执行时直接返回已有的调用。批准提交以后再交给 Worker 启动。

| 计划模式 | 流程 |
|---|---|
| `none` | 主调用（发送阶段目标）→ 可选审阅 → 完成 |
| `current` | 依赖完成即分派各项 → 可选审阅 → 汇总 → 完成 |
| `agent` | 拆分调用（`PLAN_INSTRUCTION`）→ 读回计划（只允许规则内的 Agent）→ 同 `current` |

- **审阅**：调用要求第一行写 `VERDICT: PASS` 或 `VERDICT: FAIL`，交接内容是各项结果，请求里附上阶段目标和完成标准。解析不出结论按 FAIL 处理。
- **完成**：Hub 根据记录在本地生成完成总结，不额外调用模型。总结包括各步骤和结果、审阅结论、汇总回复所在消息、调用数和用量。阶段结束后不会自动开始下一阶段。
- **失败**（P4.6a）：某一步失败、没有回复、状态未知、审阅 FAIL、达到调用上限，或被 Hub 限额拒绝时，阶段按阻塞结束，总结写明失败步骤、原因、已完成的进度和继续所需的条件。自行修复重试是 P4.6b 的内容。
- **名额**：同时运行的子任务数不超过树策略的并发上限。暂时没有名额的已批准调用保留到下一次推进。阶段批准的审批有效期为 24 小时；执行入口照样检查阶段状态。
- **后台循环**：`serve.py` 启动时同时启动后台循环，默认每 2 秒推进一次。测试中不启动它，直接调用 `tick()`。

## 4. 接口与页面

- **接口**：
  - `GET /api/conversations/{cid}/stage`：当前阶段的状态、规则、事件，以及哪些 Agent 在哪种执行边界下已经跑通。
  - `POST /api/conversations/{cid}/stages`：启动阶段，只有用户能调用。
  - `POST /api/stages/{id}/pause | resume | stop`：暂停、继续、停止。停止会撤销本阶段已批准但还没执行的调用，停止后不会自动恢复。
- **右栏“自动执行”分区**：
  - 表单：目标、完成标准、执行边界和监督同意、计划模式、各角色 Agent、调用上限、命令前缀、是否允许改文件；
  - 启动前用确认框把目标、规则和上限完整显示一次；
  - 状态卡：当前状态、步骤、调用数、暂停 / 继续 / 停止按钮、完成或阻塞总结，以及最近的自动批准记录。
- **顶栏**：阶段进行中时，常驻一个状态标记和暂停、停止按钮。
- **卡片**：由规则批准的调用卡标“按阶段规则自动批准”。工具卡标“按阶段规则自动允许 / 拒绝”和对应规则。
- **按钮改名**：手动按钮改为“启动本次调用 / 不启动”和“允许此操作 / 拒绝此操作”。

## 5. 后续步骤

- **P4.6b**：失败分类；以“阶段和步骤”为单位计重试次数（存在数据库里，重启也不清零）；修复调用要包含失败事实和上一次的做法，并且输入不能和以往任何一次相同；用完重试次数或遇到无法重试的情况时，写出阻塞总结。
- **P4.6c**：适配器新增“接入方额度耗尽”结果（带恢复时间和额度桶，识别规则保守）。新增等待表，记录下次检查时间：有恢复时间就等到那时；没有就从 5 分钟逐步加长，最长 60 分钟。同一额度桶同一时间只让一个任务探测；等待不消耗普通错误的重试次数。用虚拟时钟测试，并测重启后恢复。真实接入方的额度错误格式**未验证**。
- **P4.6d**：桩场景加演示步骤，请用户操作验收后收口，再跑一次全量测试。

## 6. 不认定

- 离线通过不代表真实接入已验证。真实运行按用户授权另行申请。
- 自动模式不扩大适配器原生工具或子 Agent 的可控范围，用户监督模式的边界照旧。
