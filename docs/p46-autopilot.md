需求见 `E:\plug\AGENT_HUB_AUTOMATION_REQUIREMENTS.md`。2026-10-26：P4.6a/b/c 的代码与离线验证已补齐；P4.6d 的用户操作验收待进行，步骤见 [离线验收指南](p46-offline-acceptance.md)。本文不授权任何真实运行。

## 1. 授权模型

- 授权仍只有一个执行入口：`PolicyService.consume`。它在事务里核对快照、策略版本、审批、停止和暂停状态以及名额，通过后才启动适配器。P4.6 不新增绕过它的路径。
- 授权有两种来源：
  - **逐次同意**（手动模式）：沿用现有审批卡。
  - **阶段授权**（自动模式）：登录用户在页面上启动一个阶段时，后端写一条阶段记录（`stage_runs`），内容包括目标、完成标准、规则、执行边界和规则哈希；用户监督模式的边界同意也在这里勾一次。
- 调度器为阶段内的每一步生成普通调用和审批，然后按规则代为批准，并写一条授权来源记录（`stage_grants`：审批 → 阶段、步骤、规则）。
- 执行入口新增一项检查：凡是由阶段批准的调用，阶段必须仍在进行中，且没有过期；否则拒绝（`stage_not_active`），适配器不启动。所以阶段暂停、停止或过期后，已批准但还没执行的调用也启动不了。
- 规则只能由登录用户通过接口设置。Agent 的回复只能提出计划内容和工具请求，不能修改规则，也不能给自己授权。
- **前置条件“先跑通一次”**：
  - 启动阶段时，对规则里的每个 Agent 检查是否已有一次满足以下条件的成功调用：同一登录用户、同一 Agent、同一适配器身份（binding）、同一执行边界，由用户逐次批准（不是阶段批准）。没有就拒绝（`stage_not_proven`）。
  - 身份必须相同，所以用桩跑通的只能开启模拟的自动执行。
- 计划需要子任务时，启动阶段会顺带开启协作扩展。开启协作会生成新的策略版本，按现有规则作废未消费的手动审批，页面在确认框里提前说明。

## 2. 阶段规则（契约 `agenthub.stage`）

| 字段 | 含义 |
|---|---|
| `agents` | 允许使用的 Agent |
| `plan` | `none`：不拆分，由主 Agent 单次完成；`current`：沿用会话里最新的手写计划；`agent`：先请主 Agent 拆分，读回后执行 |
| `main_agent` / `review_agent` / `collect_agent` | 主调用、审阅（可不设）、汇总使用的 Agent，都必须在 `agents` 里 |
| `max_calls` | 本阶段最多由规则批准的调用数（1–50），同时仍受树策略的调用上限和预算约束 |
| `tool.command_prefixes` | 允许自动放行的命令前缀，每行一条 |
| `tool.allow_file_changes` | 是否自动放行文件修改请求 |
| `retry_limit` | 普通错误首次失败后的重试次数，0–3，默认 3 |
| `auto_resume` | 额度恢复后是否自动续跑，默认开 |
| `quota_retry_seconds` | 未知恢复时间的首次检查间隔，60–3600 秒，默认 300；页面以分钟填写 |
| `paper`（P6，可选） | 仅当 `plan == "paper"`：论文研究任务 ID、请求哈希、资源规则（`agenthub.papers.ResourceRules`）及其哈希。只能由 `/api/papers` 创建，通用阶段表单不接受；未设置时不进入 `as_dict`，原有阶段哈希不变。见 [P6 实现](p6-implementation.md) |

工作目录沿用已核验适配器配置；并发、累计子任务数和 Token 预算沿用根任务策略。阶段不提高这些限制。规则创建后不可原地改写；要改规则，停止旧阶段并授权一个新阶段。数据库规则哈希或适配器身份变化会使原阶段不能继续启动。

**工具规则**（`agenthub.stage.tool_decision`，纯函数）：
- 只对 Codex app-server 有意义。Claude Code CLI 本来就关了工具。
- 命令请求自动放行，需同时满足：
  - 命令能被拆成参数；
  - 有效命令（去掉 PowerShell 或 cmd 外壳后）以某条前缀开头，且在单词边界处结束；
  - 不含 `;`、`&&`、`||`、`|`、`>`、`<`、反引号、`$(` 等串接或重定向符号；
  - 如果命令里出现敏感词（删除、推送、合并、部署、联网下载等），匹配的那条前缀本身必须写出这个词。例如前缀 `git` 不能放行 `git push`，必须单独写 `git push`。
- 文件修改请求只在 `allow_file_changes` 为真时放行。扩大可写根目录（`grantRoot`）的请求一律拒绝。
- 其余请求自动拒绝，不等人点。拒绝原因写进卡片和阶段事件，Agent 收到拒绝后可以换办法。
- 真实 app-server 的普通命令/文件请求可由阶段规则逐次决定，详见 [工具审批](codex-tool-approval.md)。额外权限、托管网络与整场会话范围不由普通前缀/文件规则授予；适配器被显式设为只能拒绝时，允许仍会改为拒绝。
- 阶段暂停后停止自动决定工具卡，阶段调用的工具决定也不能发给 provider；继续阶段后重新按规则处理尚未过期的卡。暂停不保证已经执行的操作停下，工具卡自身的等待期限也不会冻结。

## 3. 调度（P4.6a）

`agenthub_kernel.autopilot.Autopilot.tick()` 每次推进所有进行中的阶段。每一步都在 `BEGIN IMMEDIATE` 里创建调用，`client_request_id` 由阶段和步骤固定生成，重复执行时直接返回已有的调用。批准提交以后再交给 Worker 启动。

| 计划模式 | 流程 |
|---|---|
| `none` | 主调用（发送阶段目标）→ 可选审阅 → 完成 |
| `current` | 依赖完成即分派各项 → 可选审阅 → 汇总 → 完成 |
| `agent` | 拆分调用（`PLAN_INSTRUCTION`）→ 读回计划（只允许规则内的 Agent）→ 同 `current` |

- **审阅**：调用要求第一行写 `VERDICT: PASS` 或 `VERDICT: FAIL`，交接内容是各项结果，请求里附上阶段目标和完成标准。解析不出结论按 FAIL 处理。
- **完成**：Hub 根据记录在本地生成完成总结，不额外调用模型。总结包括各步骤和结果、审阅结论、汇总回复所在消息、调用数和用量。阶段结束后不会自动开始下一阶段。
- **失败**：普通执行失败、没有结果、不可读计划进入有次数上限的修复；未知执行状态、用户取消、规则外计划、预算/调用上限或启动门禁拒绝直接阻塞。总结关联失败调用、执行模式、续接方式、已完成进度、重试记录和继续所需条件。输入及错误详情仍在原调用记录里。
- **名额**：同时运行的子任务数不超过树策略的并发上限。暂时没有名额的已批准调用保留到下一次推进。阶段授权默认持续至完成、阻塞或用户停止，阶段审批不套用手动审批的短期 TTL，也没有固定 24 小时过期；每次执行仍检查阶段状态和根任务策略。
- **后台循环**：`serve.py` 默认每 2 秒推进一次；启动时先执行 Worker 恢复。测试注入时钟并直接调用 `tick()`。每个阶段使用数据库写事务推进；调用创建、检查点、额度探测占用同事务保存。某个阶段出现内部异常时，回滚这次推进并留下阻塞总结，不不断重放该阶段。

## 4. 接口与页面

- **接口**：
  - `GET /api/conversations/{cid}/stage`：当前阶段的状态、规则、事件，以及哪些 Agent 在哪种执行边界下已经跑通。
  - `POST /api/conversations/{cid}/stages`：启动阶段，只有用户能调用。
  - `POST /api/stages/{id}/pause | resume | stop`：暂停、继续、停止。停止会撤销本阶段已批准但还没执行的调用，并向本阶段仍运行的调用请求中断；返回适配器确认或 unsupported，不能将阶段停止等同于远端已经停止。停止后不会自动恢复。
- **右栏“自动执行”分区**：
  - 表单：目标、完成标准、执行边界和监督同意、计划模式、各角色 Agent、调用上限、修复次数、额度自动续跑、未知恢复时间的检查间隔、命令前缀、是否允许改文件；
  - 启动前用确认框把目标、规则和上限完整显示一次；
  - 状态卡：当前状态、步骤、调用数、修复计数、恢复/下次检查时间、暂停 / 继续 / 停止按钮、完成或阻塞总结，以及最近的自动批准记录。等待时间按浏览器本地时区显示。
- **顶栏**：阶段进行中时，常驻一个状态标记和暂停、停止按钮。
- **卡片**：由规则批准的调用卡标“按阶段规则自动批准”。工具卡标“按阶段规则自动允许 / 拒绝”和对应规则。
- **按钮改名**：手动按钮改为“启动本次调用 / 不启动”和“允许此操作 / 拒绝此操作”。

## 5. 修复重试（P4.6b）

- 计数按阶段内的逻辑步骤保存，换调用 ID 或重启不清零。审阅失败 → 主 Agent 修复 → 重新审阅共用 `review_cycle` 计数，最多三次修复，不能通过新审阅节点重新获得次数。
- SQLite 中同秒创建的子任务调用，以插入次序打破时间戳平局，不按随机调用 ID 排序；避免已完成的重试被旧失败记录遮住，造成计划一直等待。
- 修复请求带有原目标、依赖结果、上次错误和可用的上次输出，并指示先找原因、换方法、再验证。每次请求带不同修复序号，不能原文重复重放。模型是否真正改变方法仍由结果和审阅判断，Hub 不声称能证明其思考过程。
- 审阅 FAIL 会把审阅意见交给主 Agent 修复，再审阅修复后的结果。未设审阅 Agent 时，以完成调用并收到回复作为本阶段的自动完成依据；业务质量需要用户确认。
- 调用和预算上限可能早于三次修复用尽；不会擅自扩额。额度等待后的普通失败会重新进入修复分类。

## 6. 额度等待与恢复（P4.6c）

- Codex app-server 的失败事件/RPC 错误与 Claude Code 的失败结果，通过 `agenthub_adapters.quota.quota_error` 生成 `provider_quota = {kind, reset_at}`。只识别明确的 429、quota/rate/usage limit 错误。安全防护、鉴权、上下文过长不伪装成额度等待。成功回复不参与识别。
- 只接受机器可读的带时区 reset 时间、时间戳或数字 Retry-After；不猜自然语言钟点。未知恢复时间从阶段设定的间隔开始（默认 5 分钟），再次限额则翻倍，最长 60 分钟。
- `provider_quota` 保存额度桶、下次检查、退避、失败来源和探测调用。当前一个 Hub 对每个接入方只有一个凭据配置，因此桶按 Agent 划分；多账号额度桶未实现。同桶后来的阶段共用已经存在的等待及探测，不各自密集请求。
- 没有接入只读额度查询接口；一次受规则约束的续跑调用用来确认恢复，仍计入调用和实际用量。额度失败不占普通修复次数；预算和调用上限保持有效。
- 原步骤、依赖结果、重试次数、调用 ID 保存在 `stage_runs.checkpoint`。已完成计划节点跳过；未知执行状态阻塞，不能为了恢复重复启动。
- Codex 有已记录的原生 thread 时绑定该失败调用自己的 thread 恢复；Claude Code 没有原生续接能力，使用原目标、依赖结果和失败记录新开独立调用。`recovery_started` 事件记录 native_resume / independent。原生续接明确失败后，按普通修复路径建立独立调用；未知结果不能如此重试。
- 用户关闭自动续跑后需要点“继续”；另一个阶段恢复额度也不会代替此用户决定。暂停/停止优先于到点恢复。
- 关页面不影响后台；重启服务使用相同数据目录才可恢复。关机期间不会执行，重新启动后的恢复检查会处理已到期的等待。
- 探测调用只有在**能证明从未启动**时才释放租约。调用仍是 `draft`/`awaiting_approval` 且其审批已是 `revoked`/`declined`/`expired`（或审批已不存在）时，记 `quota_probe_stranded` 事件、清空 `provider_quota.probe_invocation_id`，由下个 tick 重新探测；审批仍是 `pending`/`approved`、或调用已 `queued`/`starting`/`running`/`unknown` 时继续等待，绝不重复执行可能已开始的调用。否则一次"暂停后审批被撤销"会让额度桶被一条永不启动的调用永久占住，后续阶段全部卡在"等待额度恢复"。

## 8. 不认定

- 离线通过不代表真实接入已验证。真实运行按用户授权另行申请。
- 自动模式不扩大适配器原生工具或子 Agent 的可控范围，用户监督模式的边界照旧。
